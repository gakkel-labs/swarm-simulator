## Vue d'ensemble : santé globale **bonne**

- 0 TODO/FIXME dans le code source
- 144 `@Test` sur ~20 classes, AssertJ + Mockito, conventions respectées
- Records, sealed-friendly, `AtomicReference` sur `Target`, validation dans `BoidsConfig`
- Pas de dead code visible, packages bien découpés

La dette est principalement structurelle / anticipative.

## 🔴 Dette importante (à traiter avant v0.2)

### 1. Module `tests/` vide
`tests/pom.xml` existe mais zéro `.java`. Aucun test d'intégration bout-en-bout (client gRPC → serveur → WorldState). Tous les tests sont unitaires. La conversion de coordonnées NED↔server↔Unity (3 transformations distinctes) n'est validée nulle part de bout en bout.

### 2. Conversion de coordonnées dupliquée et fragile
- `SwarmObserverImpl.toVec3` (`SwarmObserverImpl.java:154-163`) : server→NED
- `SimulationControlImpl.placeTarget` (`SimulationControlImpl.java:38`) : NED→server
- `SwarmVisualizer.NedToUnity` (`SwarmVisualizer.java:254`)
- `TargetRenderer.NedToUnity` (`TargetRenderer.java:70`)
- `TargetPlacer` (`TargetPlacer.java:42-47`) : Unity→NED inverse

5 implémentations indépendantes du même mapping. Une erreur sur un axe = bug de positionnement difficile à isoler. À centraliser : utilitaire serveur + utilitaire Unity, testés.

### 3. `SimulationLoop.main()` dupliqué
`SimulationLoop.java:353-372` : un `main()` qui démarre la boucle sans serveur gRPC. Probable vestige d'exploration. Source de confusion — un dev pourrait le lancer en pensant lancer le simu réel. À supprimer (le vrai entrypoint est `SwarmServer.main`).

### 4. `Predator` : volatiles non-atomiques
`Predator.java:11-12` — `position` et `velocity` sont `volatile` mais mis à jour séparément dans `update()`. Un futur observateur (autre thread) peut lire un couple (position t+1, velocity t). C'est latent : aujourd'hui seul le sim-thread lit, mais `Agent` a déjà été refactorisé pour le problème équivalent et `Target` utilise `AtomicReference`. Cohérence à rétablir avant d'exposer un canal de lecture parallèle.

## 🟡 Dette modérée

### 5. Magic numbers hardcodés en plusieurs endroits
- ~~`SimulationLoop.SENSOR_RADIUS = 20.0`~~ → déplacé dans `SimulationConstants.SENSOR_RADIUS_M` (2026-05-21)
- `Predator.SPEED = 3.0` / `EAT_RADIUS = 1.5` (`Predator.java:8-9`) — non configurables, non testables avec d'autres valeurs
- `SwarmVisualizer.SpawnFloor` (`SwarmVisualizer.java:354-365`) : position du sol codée en dur (`Y=-100`, scale 10×5) avec un commentaire qui dit que ça correspond aux dimensions serveur. Si on change `DEFAULT_WORLD_*` côté Java, le sol est désaligné silencieusement. Le `WorldState` proto pourrait porter les dimensions.

### 6. `Random` non déterministe dans `BoidsRules`
`BoidsRules.java:16` : `new Random()` sans seed. `wander()` n'est pas reproductible entre runs → tests fragiles côté simu, replay impossible. Une seed (env var ou flag) résoudrait.

### 7. Aucune configuration externalisée
Port 50051, agentCount=20, configs Boids, dimensions monde — tout en dur. Pour v0.2 (Docker) il faudra de toute façon paramétrer. Un `application.properties` minimal ou variables d'env suffirait, pas besoin de Spring.

### 8. `World.neighbors()` en O(n²)
`World.java:67-74` — acceptable à 20 agents (400 ops × 30 Hz). À 100 agents (10k ops/tick) ça reste OK mais commence à coûter. Si la roadmap v0.4 vise des essaims plus gros, une grille spatiale uniforme s'impose.

### 9. ADRs lacunaires
`docs/adr/` ne contient que `0004` (et le TEMPLATE). Les décisions structurantes (pas de Spring, gRPC streaming, NED, immutability strategy) ne sont pas tracées en ADR alors que CLAUDE.md y fait référence.

### 10. Cast unchecked dans `SwarmObserverImpl`
`SwarmObserverImpl.java:60` — `(ServerCallStreamObserver<WorldState>) responseObserver` sans vérification de type. gRPC le garantit en pratique mais un commentaire ou `instanceof` rendrait l'invariant explicite.

## 🟢 Détails mineurs

### 11. `SwarmObserverImpl` : effet de bord en constructeur
`SwarmObserverImpl.java:52` démarre le `scheduleAtFixedRate` dans le ctor. Complique les tests (déjà contourné avec un ctor package-private + executor mocké). Une méthode `start()` séparée serait plus propre.

### 12. `predator-0` hardcodé
`SwarmObserverImpl.java:131` : ID prédateur fixe. Si v0.x ajoute plusieurs prédateurs, à refactorer.

### 13. `Vector3D.distanceTo` alloue temporaire
`Vector3D.java:32` : `subtract(other).magnitude()` crée un objet. Sur le hot path 30 Hz c'est négligeable aujourd'hui, mais `World.neighbors` a déjà sa propre `squaredDistance` privée — exposer `distanceSquaredTo` publique évite la duplication et l'allocation.

### 14. `World.addAgent.contains()` en O(n)
`World.java:35` — OK à 20 agents. Un `Set<UUID>` doublon serait plus propre si on scale.
