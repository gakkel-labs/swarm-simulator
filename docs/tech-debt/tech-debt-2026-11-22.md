## Before Step 2 (blocking for the optimizer)

### 1. No simulation clock
The loop follows the computer clock: `scheduleAtFixedRate`, the respawn delay (5 s), the
search time (`Target` uses `System.nanoTime()`) and the CSV export. The `WorldState` timestamp
already comes from a `java.time.Clock` that tests can replace (#152). Two runs with the same seed drift apart,
and a run cannot go faster than real time. **Fix:** a simulation clock and a `step(dt)` engine
that the optimizer can call in a loop, with no thread.

### 2. `WorldState` is not one exact moment
See [ADR-0008](../adr/0008-shared-world-concurrency.md): one frame can mix two ticks. Fine on
screen, not fine for a score or a replay. **Fix:** publish an immutable snapshot at the end of
each tick.

### 3. ~~`tests/` module is empty~~ — resolved
See "Resolved since May".

## Domain and naming (DDD)

### 4. `Predator` must become the danger
The glossary says **danger** (a surface ship, a fishing net, an animal, a no-go area). The code
and the contract still say `Predator`, `PredatorState`, `predatorFlee`, `threatFlee*`. Rename in
the domain first; the proto message can only change with a new package version (`v2`) or by
adding a new field.

### 5. `height` and `depth` of the world are confusing
In the backend, `height` is the water column (Up/Down) and `depth` is the North extent
([ADR-0007](../adr/0007-coordinate-frames.md)). For a marine reader, "depth" means the water
column. **Fix:** rename to names that say the axis (for example `eastExtent`, `waterColumn`,
`northExtent`) and to the glossary word: the world is the **search area** (`SearchArea`).

### 6. Two Java package prefixes for the contracts
`swarm_observer.proto` generates `io.gakkel.swarm.contracts.v1`; `ping.proto` generates
`fr.gakkel.swarmsimulator.contracts`. Choose one prefix the next time the contract changes
version.

## Moderate

### 7. Fixed values in the code
`SimulationConstants.SENSOR_RADIUS_M = 10`, respawn delay and distance in `SimulationLoop`.
They cannot be set like the Boids weights (the danger values can, since #152).
The optimizer will want to change at least the sensor radius.

### 8. The Unity floor follows the server size by hand
`SwarmVisualizer.SpawnFloor()` (used when there is no seabed) places a floor that must match
the server world size. Since #152 `WorldState` sends `search_area_size_m`; Unity still has to
use it, so a change of `SWARM_WORLD_*` is seen on screen.

### 9. Obstacles are spheres
The server knows only spheres; Unity draws chimneys standing on the seabed. A drone can pass
under the sphere and through the chimney on screen (issue #142).

### 10. `World.neighbors()` is O(n²)
Fine at 20 drones. Many runs with bigger swarms (Step 2) will need a spatial grid.

See "Resolved since May".
